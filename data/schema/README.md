# data/schema

Canonical snapshot of the SQLite schema. `schema.sql` is generated by applying `data/migrations/*.up.sql`
in order to a scratch DB and dumping `sqlite_master`; never edit it by hand. Current through `0001_init`.

## Conventions recorded here (T015 and T016 follow these)

- **Migration files**: `NNNN_name.up.sql` + `NNNN_name.down.sql`. The runner (T015) applies each file in one
  transaction and owns its own `schema_migrations` bookkeeping table (not part of the migrations). PRAGMAs
  (`journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout=5000`) are set by the connection, never inside a migration.
- **Ids**: server-generated **UUIDv7**, lowercase hyphenated text, for every table's `id` (states, edges,
  network_calls, and also runs, forms, frontier, actions, ...) so T016 has one generator. `states.fingerprint`
  is a separate UNIQUE column, not the id. `actions.id` is the `action_id` handed to the agent.
- **Timestamps**: UTC ISO 8601 text with milliseconds and `Z`, e.g. `2026-01-01T00:00:00.000Z`
  (`new Date().toISOString()`). Lexicographic order equals chronological order. The app supplies them;
  there are no column defaults. Durations are integer milliseconds (`runs.elapsed_ms`).
- **JSON**: `TEXT` guarded by `CHECK (json_valid(...))`; `console_errors` is a JSON array text column
  (`json_type = 'array'`, default `'[]'`). Booleans are `INTEGER` 0/1 with a CHECK.
- **evidence_ref**: `<sha256>.<ext>` filename relative to `data/evidence/`; CHECK non-empty. NOT NULL with a
  confidence-enum CHECK on `states`, `edges`, `forms`; `state_observations` and `rule_candidates` also require
  `evidence_ref`. `network_calls` deliberately carries neither `evidence_ref` nor `confidence`.
- **Enums**: CHECK-constrained for status/safety_class/confidence/stabilization/kind. `runs.mode` has no CHECK
  (FR-022: `trace` must not need a migration); Zod enforces it.

## Design decisions

- **Frontier**: one `frontier` table holds the queue and the history. Statuses: `pending`, `done`, plus the five
  skip statuses (`skipped_unsafe | out_of_scope | denylisted | budget_reached | unreachable`; those require a
  `reason`). `get_next_frontier_item` returns the highest `priority`, then oldest `id`, `pending` row of the run
  without mutating it; `act` moves the row to `done` or to a skip status. Resume (FR-020) simply continues from
  `pending` rows. Visited set = `state_observations` for the run plus `frontier.status='done'`; no separate table.
- **Action ids**: persisted in `actions` (with `state_id`, safety class, `allowed`, `skip_reason`). `act` validates
  `action_id` against this table and that its `state_id` is the current state; otherwise `UNKNOWN_ACTION`.
- **State observations**: `states` are global by fingerprint; `state_observations(run_id, state_id)` PK
  (`WITHOUT ROWID`) with FKs to `runs` and `states` answers `get_known_states(run_id, cluster_id?)`.
- **Decision log (FR-021)**: `decision_log` table (kinds `skip | refuse | merge | split | warning`) written through
  the DB; pino mirrors each entry to stdout/JSONL but the table is the record. Reason: it must be queryable
  across runs and survive resume.
- **Indexes**: `ux_states_fingerprint` (record_state idempotency), `ix_states_cluster_id` (get_known_states),
  `ix_edges_run_id` (coverage/finish_run), `ix_frontier_queue(run_id, status, priority DESC, id)`
  (get_next_frontier_item; also serves run_id lookups). `state_observations` uses its PK.
