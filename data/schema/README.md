# data/schema

Canonical snapshot of the SQLite schema. `schema.sql` is generated by applying `data/migrations/*.up.sql`
in order to a scratch DB and dumping `sqlite_master`; never edit it by hand. Current through
`0037_amendment_anchors`. `0032_transitions_observations` renamed v1's `edges` to `transitions` and `page_visits` to
`observations`, spec 039 T110; older notes below use the new names). `0035` dropped v1's
`reconciliations` and `rule_candidates` (hypotheses replace them, spec 039 T076). `0036` renamed
`process_variants` / `process_variant_revisions` to `process_models` / `process_model_revisions`
(their `variant_id` columns keep the name) and makes a PROC record need its process
(`doc_records.process_id`, one per process, enforced by an index and two triggers). `0037` anchors
amendments on `entity_refs` (`amendments.ref_id`: a model screen and an element key); amendments
without one keep the v1 fingerprint anchor.

## Conventions recorded here (T015 and T016 follow these)

- **Migration files**: `NNNN_name.up.sql` + `NNNN_name.down.sql`. The runner (T015) applies each file in one
  transaction and owns its own `schema_migrations` bookkeeping table (not part of the migrations). PRAGMAs
  (`journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout=5000`) are set by the connection, never inside a migration.
- **Ids**: server-generated **UUIDv7**, lowercase hyphenated text, for every table's `id` (states, transitions,
  network_calls, and also runs, forms, frontier, actions, robots_policies, portal_data_log, ...) so T016 has
  one generator. `states.fingerprint` is unique per portal, not globally, and is not the id. `actions.id` is
  the `action_id` handed to the agent.
- **Timestamps**: UTC ISO 8601 text with milliseconds and `Z`, e.g. `2026-01-01T00:00:00.000Z`
  (`new Date().toISOString()`). Lexicographic order equals chronological order. The app supplies them;
  there are no column defaults. Durations are integer milliseconds (`runs.elapsed_ms`).
- **JSON**: `TEXT` guarded by `CHECK (json_valid(...))`; `console_errors` is a JSON array text column
  (`json_type = 'array'`, default `'[]'`). Booleans are `INTEGER` 0/1 with a CHECK.
- **evidence_ref**: `<sha256>.<ext>` filename relative to `data/evidence/`; CHECK non-empty. NOT NULL with a
  confidence-enum CHECK on `states`, `transitions`, `forms`; `state_observations` also requires
  `evidence_ref`. `robots_policies.evidence_ref` is NOT NULL and non-empty too (always written, even for a
  404 or failed fetch), but carries no confidence enum: a robots fetch is a log, not an inferred record.
  `network_calls` deliberately carries neither `evidence_ref` nor `confidence`.
- **Enums**: CHECK-constrained for status/safety_class/confidence/stabilization/kind/outcome/action. `runs.mode`
  has no CHECK (FR-022: `trace` must not need a migration); Zod enforces it.
- **Layer B keys** (`0004_ba_documentation`, R-13): `doc_records.key` is `<PREFIX>-<seq>`, `seq` zero-padded
  to 3+ digits (`REQ-017`), `UNIQUE(portal_id, key)`; prefix per `kind` (capability→CAP, screen→SCR,
  process→PROC, use_case→UC, requirement→REQ, nfr→NFR, business_rule→BR, glossary_term→GL, data_item→DI,
  assumption→ASM, open_question→OQ, followup→FUP; `KEY_PREFIX` in `@pathfinder/core/schemas/doc-record.ts`).
- **Polymorphic evidence targets**: `doc_evidence_links.target_id` (and Layer A's `open_questions.about_ref`)
  carry no FK; the target's kind names the table and the writing tool resolves
  and validates it (portal/run membership) before the row is inserted. `docs:audit` re-checks resolvability.
- **Status only changes through the status engine**: `doc_revisions.status` and `followup_tasks.status` are
  `NOT NULL` with a CHECK on the enum, but no write tool accepts a `status` input; only the deterministic
  status engine (`@pathfinder/docs`, research.md §4 and §11) sets them, inside the same transaction as the
  revision/review/run-lifecycle write that triggers the change.

## Design decisions

- **Frontier**: one `frontier` table holds the queue and the history. Statuses: `pending`, `done`, plus the six
  skip statuses (`skipped_unsafe | out_of_scope | denylisted | robots_disallowed | budget_reached | unreachable`;
  those require a `reason`). `get_next_frontier_item` returns the highest `priority`, then oldest `id`, `pending`
  row of the run without mutating it; `act` moves the row to `done` or to a skip status. Resume (FR-020) simply
  continues from `pending` rows. Visited set = `state_observations` for the run plus `frontier.status='done'`;
  no separate table.
- **Action ids**: persisted in `actions` (with `state_id`, safety class, `allowed`, `skip_reason`). `act` validates
  `action_id` against this table and that its `state_id` is the current state; otherwise `UNKNOWN_ACTION`.
- **State observations**: `states` are unique per `(portal_id, fingerprint)` (0002_portal_workspaces; states
  never merge across portals, FR-026/FR-027); `state_observations(run_id, state_id)` PK (`WITHOUT ROWID`) with
  FKs to `runs` and `states` answers `get_known_states(run_id, cluster_id?)`, filtered by the run's portal.
- **Decision log (FR-021)**: `decision_log` table (kinds `skip | refuse | merge | split | warning | note`; `note`
  added by 0002_portal_workspaces for observations that did not change the run's course, e.g. the page's own
  requests to robots-disallowed URLs) written through the DB; pino mirrors each entry to stdout/JSONL but the
  table is the record. Reason: it must be queryable across runs and survive resume.
- **Robots policies (FR-001 to FR-007)**: `robots_policies` records one fetch of one host's `robots.txt` per
  row; the latest row per `(run_id, host)` is the policy in force. No index dedicated to "latest" lookups beyond
  `(run_id, host, fetched_at)`, since the query in contracts/mcp-tools.md is `ensure(host)`/`check(url)` inside
  one run's registry (in-memory), not a query against this table directly.
- **Portal data log (FR-028)**: `portal_data_log` records every `portal:export` and `portal:delete`; it has no
  FK on `portal_id` (it must survive the delete of that portal's rows) and is itself never deleted.
- **Indexes**: `ux_states_portal_fingerprint` (record_state idempotency per portal), `ix_states_portal_cluster`
  (get_known_states filtered by the run's portal), `ix_transitions_run_id` (coverage/finish_run),
  `ix_frontier_queue(run_id, status, priority DESC, id)` (get_next_frontier_item; also serves run_id lookups),
  `ix_robots_policies_run_host_fetched` (latest policy per host within a run). `state_observations` uses its PK.
  `ix_doc_evidence_links_run_id` (run → records reverse lookups, FR-033) and `ix_doc_evidence_links_target`
  (`get_evidence(target_kind, target_id)`) are the only indexes added by `0004_ba_documentation`; `list_records`
  is served by the `UNIQUE(portal_id, kind, seq)` index already required for key allocation (no extra index).
- **Layer B (`0004_ba_documentation`, R-13)**: eight tables add the BA deliverable — `analysis_sessions`,
  `analysis_session_runs`, `doc_records`, `doc_revisions`, `doc_evidence_links`, `doc_relations`,
  `doc_reviews`, `followup_tasks` — per `specs/004-ba-documentation/data-model.md`. Generic record tables
  with per-kind content validated by a Zod discriminated union (`@pathfinder/core/schemas/doc-content.ts`),
  not one table per kind (research.md §3). `doc_revisions.responds_to_review` forward-references
  `doc_reviews`, created later in the same file; safe because SQLite does not check a referenced table's
  existence at `CREATE TABLE` time and both tables exist by the time `foreign_key_check` runs at commit.
  `doc_evidence_links.target_kind` values `process`/`process_step` resolve to the 0005 tables below.
- **Relation triples (`0013_relation_triples`, spec 019 F-12)**: the `doc_relations.type` CHECK cannot see the
  record kinds, so two triggers (`trg_doc_relations_triple_insert`, `..._update`) look up the kinds through
  `doc_revisions.record_id` → `doc_records.kind` and `RAISE(ABORT, 'RELATION_NOT_ALLOWED: ...')` on a triple
  outside the list. The list equals `RELATION_RULES` (`@pathfinder/docs`); `docs/tests/relation-triples.test.ts`
  derives every triple from it and fails on drift. The server's `RELATION_NOT_ALLOWED` refusal stays first (it
  names what is allowed); the trigger is the backstop for any other write path. A new relation type or triple
  needs a migration that replaces the triggers (and a CHECK rebuild for a new `type`). This is the first
  trigger in the schema; the snapshot keeps triggers (they are in `sqlite_master`).
- **Screens and amendment revisions (`0015_screens`, `0016_amendment_revisions`, spec 022)**: `screens` plus
  `states.screen_id`/`screen_rev` (ALTER, backfilled; `ux_states_screen_rev`); `amendments` rebuilt for the status
  vocabulary `active | needs_reanchor | dismissed | withdrawn` and the `rev`/`screen_id` columns; `amendment_revisions`
  is append-only. Details: `specs/022-salvage-redesign/data-model.md` "As built".
- **Chat proposals (`0017_chat_proposals`, spec 022 R6)**: `chat_proposals` holds changes the chat assistant
  proposes (`target_kind` `amendment` | `new_amendment`, `payload` JSON object, one-line `summary`) and a person
  applies, discards or finds stale. CHECKs: an `amendment` proposal has `target_id` and `base_rev`, a
  `new_amendment` has neither; `applied` needs `applied_amendment_id`, `applied_rev` and `decided_at`;
  `discarded`/`stale` need `decided_at`. Indexes `ix_chat_proposals_conversation (conversation_id, created_at)`
  (drawer) and `ix_chat_proposals_portal_status (portal_id, status)` (Review inbox). Written only by the chat
  service; in the portal data partition (`PORTAL_TABLES`), deleted before `amendments`.
- **BA processes (`0018_ba_processes`, spec 022 M5)**: `ba_processes` (head, key `PRC-nnn`, stage, `rev`) with
  append-only `ba_process_revisions`; `process_models` (`process_variants` until 0036; head per variant, label
  A/B/C, kind `as_is` | `to_be`) with append-only `process_model_revisions` (`steps` = JSON array of step
  objects); `process_drafts` (scratch, PK
  `(variant_id, author)`); `process_live` (append-only, newest per `(process_id, environment)` is live);
  `grouping_suggestions` (`steps` JSON array, `screens_key`); `change_spec_revisions` (`sections` JSON object).
  `base_rev` is NULL exactly for rev 1 (CHECK). Indexes: `ix_process_live_process_env`,
  `ix_grouping_suggestions_portal_status`, `ix_grouping_suggestions_portal_screens`. The up also migrates the
  newest `process_scopes` row per `(portal, name)` into a `PRC-nnn` process with variant A r1. Details:
  `specs/022-salvage-redesign/data-model.md` M5 "As built (0018)".
- **Relation rests on rule (`0020_relation_rests_on_rule`, spec 029)**: the two `doc_relations` triggers
  recreated so `depends_on` also allows `assumption → business_rule` and `use_case → business_rule`. The
  down deletes those rows and restores the 0019 triggers.
- **Relation screens (`0019_relation_screens`, R-51)**: the two `doc_relations` triggers recreated (no table
  rebuild: the types already exist) so `appears_on` also allows `glossary_term → screen` and `contains` also
  allows `process → screen`. The down deletes rows of those two triples and restores the 0014 triggers.
- **Relation vocabulary (`0014_relation_vocabulary`, spec 019 F-14)**: `doc_relations` rebuilt (CHECK, PK, STRICT,
  WITHOUT ROWID kept, rows copied) so `type` also admits `applies_on` (business_rule → screen), `asks_about`
  (open_question → any kind) and `follows_up` (followup → process, capability, screen, business_rule); both
  0013 triggers recreated with the extended list. The down deletes rows of the three new types (no old type
  can hold them) and restores the 0013 triggers.
- **Trace processes (`0005_trace_processes`, R-14)**: `processes` (one per trace run, `run_id` UNIQUE;
  `boundary_action_id` and `not_observable` required by CHECK when `outcome = 'boundary_reached'`) and
  `process_steps` (`UNIQUE(process_id, ord)`, `outcomes_json` a JSON array, `evidence_ref` non-empty,
  `confidence` enum). Written by the crawler server only; both are in the portal data partition and
  deleted before `runs`. No extra indexes: the UNIQUE constraints serve the per-process lookups.
- **Screenshots and wireframes (`0006_screenshots_wireframes`, R-20 + R-21, spec 008)**: `states` gains
  nullable `screenshot_ref` (`<sha256>.png`) and `layout_ref` (Layout JSON: element keys and page-coordinate
  boxes), set once when the state is first recorded; no backfill. `state_wireframes` (one row per state,
  derived, `generator_version` marks stale rows) points at the `.svg` and `.excalidraw` blobs.
  `doc_evidence_links` is rebuilt: `target_kind` adds `screen_region` (target_id = state id) and a nullable
  `region` column holds the element key, with `CHECK ((target_kind = 'screen_region') = (region IS NOT NULL))`.
  The down migration turns screen-region links into state links and keeps the key in `note`.
  `state_wireframes` is in the portal data partition and is deleted before `states`.

## Trace (0003_trace, R-17 spec 005)

- **Span model**: `trace_boots` is one row per MCP server process (its `trace_level`/`pw_trace`
  config, `pid`, `version`); `trace_spans` is one row per `call` (one MCP tool invocation), `phase`
  (a named step inside a call, e.g. `settle`, `robots_fetch`) or `event` (a point-in-time fact —
  `gate_decision`, `robots_check`, `decision`, `obstacle`, …). `phase` and `event` spans nest under a
  `call` via `parent_id`; `call` spans have `parent_id IS NULL`. The vocabulary of `name` values is
  fixed by `specs/005-crawl-run-observability-trace/contracts/trace-spans.md`, not by a CHECK, so new
  phase/event names don't need a migration.
- **Ordering**: spans of one process are strictly ordered by `trace_spans.seq` (unique per
  `boot_id`); across a crash/resume, order by `trace_boots.started_at` then `seq` (`ix_trace_spans_run`
  covers `(run_id, parent_id, boot_id, seq)` for both the call list and child expansion).
- **Run-less spans**: `run_id` is nullable — calls that are refused before a run exists (e.g. a
  `start_run` preflight failure) or that never belong to a run stay attached only to their boot, and
  are surfaced separately as "server activity" rather than under any run. `between_calls = 1` marks an
  `event` that belongs to a run but landed between two calls (no open call span to nest under).
- **Link to `decision_log`**: an `event` span with `name = 'decision'` carries `decision_id`
  referencing the `decision_log` row it announces; every `decision_log` row of a traced run has
  exactly one such span (SC-002). `ix_trace_spans_decision` serves that lookup; no FK the other way,
  since `decision_log` predates tracing and must stay writable without one.
- **`agent_turns`** is a separate, independently-populated import of the crawler's own transcript
  (via `trace:import-agent`), joined back to `trace_spans` by `tool_use_id`, not a foreign key —
  the transcript may be imported after the spans, or never.
