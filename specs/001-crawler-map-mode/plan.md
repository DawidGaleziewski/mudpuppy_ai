# Implementation Plan: Crawler Map Mode (MarketSite MVP)

**Branch**: `001-crawler-map-mode` | **Date**: 2026-09-21 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-crawler-map-mode/spec.md`

## Summary

Build the Crawler's `map` mode: a single LLM + Playwright agent, implemented as the Claude
Code subagent `.claude/agents/crawler.md`, that explores `marketsite.example` as an anonymous
guest, executing only read-only actions, and records observed states, transitions, forms and
API calls with evidence and a confidence label. The subagent's only tools are those of our
`pathfinder` MCP server, which owns the sole Playwright instance and the DB: the agent
proposes where to go, the server classifies, executes, observes, fingerprints and records. The
deterministic pieces (fingerprinting, safety classification, scope/denylist enforcement, PII
scrubbing, rate limiting, block detection, DB access) are therefore non-overridable. Portals and personas are declared as composable YAML config, validated by Zod. The
crawler runs against production under a hard environment guard: refused without an explicit
`environment: production` flag, read-only-only once running, rate-limited, and stopped
without workaround on any block or CAPTCHA.

## Technical Context

**Language/Version**: Node 22+, TypeScript (strict)

**Agent Runtime**: Claude Code subagent (`.claude/agents/crawler.md`) with an explicit
`tools:` allowlist of `mcp__pathfinder__*` only (no Bash, Edit, Write, WebFetch, WebSearch or
other MCP servers); see `research.md` §11. No LLM SDK dependency is needed.

**Primary Dependencies**: `playwright` (library, not `@playwright/test`) in `crawler`, used
in-process by `mcp-server`,
`zod` for schemas/validation, `better-sqlite3` with Kysely for storage,
`@modelcontextprotocol/sdk` for the agent-facing MCP server, `pino` for structured logging,
`yaml` for portal/persona config parsing

**Storage**: SQLite (`better-sqlite3`, one file per environment) under `data/db/` for states,
transitions, forms, API calls, frontier items, open questions and run metadata (Layer A only —
this feature does not touch Layer B/BA/QA tables); evidence (ARIA snapshots, screenshots, HAR/
network records) under `data/evidence/`, content-addressed (`sha256`), referenced by the DB.
Schema, migrations (`data/migrations/`) and the `data/schema/` snapshot are owned by the
`db-admin` subagent (`.claude/agents/db-admin.md`); see `data/README.md`.

**Testing**: Vitest for the pure packages (`fingerprint`, `safety`, `config`) against a
fixtures corpus of saved ARIA snapshots, HARs and labeled action descriptors; no
`@playwright/test` specs are generated by this feature (that is QA's role, out of scope)

**Target Platform**: Linux/macOS CLI, run locally by a maintainer or BA with network access
to the portal; not deployed as a service (per spec Assumptions)

**Project Type**: Single pnpm-workspace monorepo, one package per module (library/CLI, not a
web service)

**Performance Goals**: Not throughput-sensitive; the binding constraint is the production
rate limit and low concurrency mandated by Principle V, not agent speed

**Constraints**: Production runs MUST be read-only-only (FR-005), under a configured request
rate limit and low concurrency with an identifiable User-Agent (FR-006), refused in <5s
without the `environment: production` flag (SC-006), stopped within one detection cycle on a
CAPTCHA/block with no bypass attempt (FR-008, SC-007), and MUST cap item-listing view visits
(FR-024) and total states/depth/time/steps (FR-007)

**Scale/Scope**: One portal (MarketSite), one persona (anonymous guest), single `map`
run per invocation; `trace` mode and additional personas are out of scope but MUST NOT
require record-format or config-format changes later (FR-022)

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-checked after Phase 1 design below.*

| Principle | Status | Basis |
|---|---|---|
| I. Observed Behavior Is Separate From Intent | PASS | FR-002 restricts the crawler to observed facts, flagged inferences and open questions; no business-intent claim is ever written as fact |
| II. Evidence and Traceability (NON-NEGOTIABLE) | PASS | FR-003 requires confidence label + evidence reference on every state/transition/form/API-call; the MCP write tools reject records missing either (see `contracts/mcp-tools.md`) |
| III. Strict Role Separation | PASS | Scope is limited to the Crawler's `map` mode only; no BA or QA logic is built here; the crawler subagent's tool allowlist contains only our MCP tools, so fingerprinting, safety classification, scope/denylist checks, rate limiting and PII scrubbing run server-side and cannot be overridden; state/transition/form/API records are written only from server-side observation |
| IV. Replay Verification Before Promotion | N/A | This feature only ever writes status `recorded` (per Principle III); promotion to `replay_verified` belongs to a future `trace`/replay feature |
| V. Safety-First Exploration (NON-NEGOTIABLE) | PASS | FR-004–FR-009, FR-024 implement the environment guard, production read-only ceiling, rate/concurrency limits, scope/denylist enforcement and CAPTCHA/block stop-without-bypass, all as code outside the agent |
| VI. Human-in-the-Loop Validation | N/A | No requirement enters `draft`/`confirmed` in this feature; open questions are recorded (FR-002) as a deliverable for later BA review only |
| VII. Deterministic Core, Pure Functions, Static Outputs | PASS | `fingerprint`, `safety` and `config` are pure, browser/LLM-free packages with Vitest fixtures; Zod schemas are the single source of truth for records and config |

### Source Code (repository root)

```text
packages/
├── core/            # Zod record schemas, SQLite access (Kysely), id generation, in-memory graph model
├── fingerprint/     # ARIA canonicalization, two-level fingerprint (exact + SimHash/MinHash), clustering — pure
├── safety/          # action classifier, denylist, environment guard — pure
├── config/          # portal.yaml / persona.yaml loaders, `extends` resolution, Zod validation
├── obstacles/       # cookie banner / popup / chat-widget handlers, shared by the crawler
├── mcp-server/      # the `pathfinder` stdio MCP server. Agent-facing tools: start_run, get_known_states,
│                    #   get_next_frontier_item, navigate, act, add_open_question, add_rule_candidate, finish_run.
│                    #   Internal recording services: record_state/transition/form/api_call, add_frontier_item, complete_run
└── crawler/         # browser runtime library used by mcp-server: preflight, session, request gate,
                     #   action gate, rate limiter, stabilizer, observer + action extractor, locators, frontier, report

.claude/agents/
└── crawler.md       # the crawler subagent definition (tool allowlist = the pathfinder MCP tools)
.mcp.json            # registers the `pathfinder` MCP server

portals/
└── marketsite/
    └── portal.yaml

personas/
├── _mixins/
└── marketsite/
    └── guest.yaml

data/                 # owned by the db-admin subagent — see data/README.md
├── migrations/        # versioned, reversible SQLite migrations (tracked)
├── schema/            # current schema snapshot, regenerated per migration (tracked)
├── db/                # actual .sqlite files, one per environment (git-ignored)
└── evidence/          # content-addressed (sha256) ARIA snapshots, screenshots, HARs (git-ignored)

tests/
├── fixtures/        # saved ARIA snapshots, HARs, labeled action descriptors
└── (per-package Vitest suites live alongside each package under packages/*/tests)
```

**Structure Decision**: Single pnpm-workspace monorepo (Option 1: single project), following
the constitution's Technical Constraints and `user_input/raw_idea/tech-stack.md` package
layout, scoped down to only the packages this feature needs (`core`, `fingerprint`, `safety`,
`config`, `obstacles`, `mcp-server`, `crawler`). Packages for later features
(`orchestrator`, `analysis`, `testgen-kit`, `runner`, `docs`, and the `ba`/`qa` agent
definitions) are intentionally not created yet.
